# AI QE Loop — Stages 1–3 Design

Date: 2026-10-10
Owner: AI QE Lead (lucaram)
Status: Draft for review

## 1. Goal

Turn the "AI quality loop with human gates" framework into a working repo for Stages 1–3:

1. **Versioned context** — pull simulated Jira, business rules, architecture and API spec into a pinned snapshot.
2. **AI generates** — Playwright planner, generator and healer produce test plans, tests and test fixes, each approved by the right role before merge.
3. **Evaluate in CI** — deterministic checks decide pass or fail; humans own the thresholds and act on failures.

Success: running the loop on story `PROJ-130` ends with a merged test plan approved by the PO, merged tagged tests approved by QE, and every CI check green.

Out of scope for now (documented in `CLAUDE.md` as later work): Stage 4 release gate, Stage 5 production observability, Stage 6 feedback skill, DeepEval and Langfuse (the mock app has no AI features).

## 2. Decisions

| Topic | Decision |
|---|---|

## 4. Mock application

- **`POST /auth/login`** implements `openapi.json`, ADR-0001 and ADR-0002 exactly:
  - correct password, not locked → `200 { token }`, `failed_attempts = 0`
  - wrong password, not locked → `401 "Wrong username or password."`, `failed_attempts += 1`; on the 5th, `locked_until = now + 15 min` and the response is `423 "Your account is locked. Try again in 15 minutes."`
  - any password while `now < locked_until` → `423` locked message; nothing changes
  - first login after `now >= locked_until` → lock cleared, `failed_attempts` treated as 0 before evaluating the attempt
  - unknown username → `401 "Wrong username or password."`, no account changed
- **Store:** in-memory map instead of PostgreSQL (simplification; same two fields as ADR-0001).
- **Test hooks** (only when `TEST_HOOKS=1`), as ADR-0001 allows:
  - `PUT /test/accounts/:username` — create or set `password`, `failed_attempts`, `locked_until`
  - `GET /test/accounts/:username` — read the same fields
- **Login page** `GET /` — form with username, password, submit; shows the `message` returned by the API (ADR-0002: UI only displays).
- Start: `npm run app` on port 3000.

## 5. Roles and approvals

`roles.json`:

```json
{
  "po":          { "users": ["lucaram"], "approves": ["context/jira-requirement/**", "context/budiness-rule/**", "specs/**"] },
  "architect":   { "users": ["lucaram"], "approves": ["context/architecture/**"] },
  "engineer":    { "users": ["lucaram"], "approves": ["context/api/**"] },
  "developer":   { "users": ["lucaram"], "approves": ["app/**"] },
  "qe":          { "users": ["lucaram"], "approves": ["tests/**", ".claude/**", "CLAUDE.md"] },
  "ai-qe-lead":  { "users": ["lucaram"], "approves": [".claude/**", "CLAUDE.md", "scripts/**", ".github/**", "roles.json"] }
}
```

`scripts/approvals.ts`:
1. Lists the PR's changed files (`gh pr diff --name-only`).
2. Works out the required roles from `approves` globs. Files that match no glob (e.g. `context/manifest.json`, `docs/**`) need no label.
3. Reads the PR's label events (`gh api repos/{owner}/{repo}/issues/{n}/events`) and, for each `approved:<role>` label currently on the PR, takes the actor of its latest `labeled` event.
4. Fails if a required role is missing or its label was added by a user not in that role's `users`. Writes a table of required / present / verified roles to the job summary.

## 6. Skills

Each skill is `.claude/skills/<name>/SKILL.md`. Every skill works on a branch, opens the PR with `gh pr create`, and lists the labels the PR needs in its body. No skill merges a PR; merging is done by a human once checks are green.

| Skill | Stage | Steps | Branch | Labels needed |
|---|---|---|---|---|
| `/pull-context` | 1 | Run `scripts/context-pull.ts`; if the manifest changed, commit and open a PR | `context/<date>` | per changed source (see `roles.json`) |
| `/plan-story <KEY>` | 2 | Read story, linked BRs, ADRs, API spec from `context/`; call the planner with the planning rules; write `specs/<KEY>-<slug>.md` | `<KEY>-plan` | `approved:po` |
| `/generate-tests <KEY>` | 2 | Refuse unless `specs/<KEY>-*.md` is on `main`; call the generator per scenario with the generation rules; run the tests locally | `<KEY>-tests` | `approved:qe` |
| `/heal-tests` | 2 | Run tests; call the healer on failures with the healer limits; if an assertion would need to change, stop and open an issue instead | `heal/<date>` | `approved:qe` |
| `/change-framework` | 1 | Edit `CLAUDE.md`, skills or agents as asked; open a PR | `framework/<topic>` | `approved:ai-qe-lead` + `approved:qe` |

**Planning rules**
- One scenario per AC, per PO clarification, and per BR `ways_to_break` entry.
- Each scenario heading carries its IDs: `[PROJ-130][AC-4][BR-001]`.
- Lock logic is planned at API level; UI scenarios only check the message is displayed (ADR-0002).
- Boundaries are always covered (e.g. 4 vs 5 attempts, lock end at 14:59 vs 15:00).

**Generation rules**
- Tags on every test: `@<KEY>`, `@AC-n` (when the scenario has one), `@BR-nnn`.
- API tests in `tests/api/`, UI tests in `tests/ui/`.
- Every API response is checked with the contract validator from `tests/support/`.
- Locked or near-locked accounts are set up through the test hooks, never by waiting.

**Healer limits**
- May change: locators, waits on elements or responses, navigation steps.
- Must not change: any `expect(...)`, expected values, tags; must not add `skip`, `fixme` or `only`.
- If a fix needs any of the above: stop, open an issue titled `Possible bug or requirement change: <test name>` with the failure output.

## 7. CI (`.github/workflows/ci.yml`)

Triggers: `pull_request` (opened, synchronize, reopened, labeled, unlabeled) and `push` to `main`.

| Job | Fails when |
|---|---|
| `typecheck-lint` | `tsc --noEmit` errors; ESLint with `eslint-plugin-playwright` (`expect-expect`, `no-skipped-test`, `no-focused-test`, `no-wait-for-timeout`) |
| `tests` | Any Playwright test fails (app started with `TEST_HOOKS=1`); HTML report uploaded as artifact |
| `contract` | Covered inside `tests`: the API client validates every response against `context/api/openapi.json` with ajv and fails the test on mismatch |
| `traceability` | A BR in `context/budiness-rule/` or an AC in a story that has a merged plan has no tagged test; or a tag references an unknown BR/AC/story. Matrix written to the job summary |
| `flaky` | A test file added or changed in the PR fails in any of `--repeat-each=5` runs |
| `assertion-guard` | On `heal/*` branches: a diff in `tests/**` adds, removes or changes a line containing `expect(`, `.skip`, `.fixme` or `.only`, or changes a `tag:` |
| `mutation` | Stryker score on `app/src/**` below `break: 60` (command runner: Playwright API tests) |
| `approvals` | See section 5 |

Label events re-trigger only `approvals` (other jobs are skipped when the event is `labeled`/`unlabeled`).

Branch protection on `main`: all jobs above required, no direct pushes, linear history.

## 8. CLAUDE.md contents

- The six-stage loop in five lines, with Stages 4–6 marked "not built yet".
- Source of truth order: `context/` (stories, BRs, ADRs, API spec) defines expected behaviour; app code and PR diffs never do.
- Tag, branch and file naming conventions.
- Approval roles and labels; "never add `approved:*` labels yourself".
- Healer limits.
- Commands: `npm run app`, `npm test`, `npm run traceability`, `npm run mutation`.

## 9. Testing the framework itself

- Unit tests (Node test runner) for `traceability.ts`, `approvals.ts` and `assertion-guard.ts` with small fixtures.
- End-to-end check: run `/plan-story PROJ-130` and `/generate-tests PROJ-130` on the real repo; expect all CI jobs green, a mutation score above 60%, and every AC-1..4 and BR-001/002 in the matrix.
- Negative checks, done once by hand: a PR with a missing label fails `approvals`; a `heal/*` PR that edits an `expect` fails `assertion-guard`; deleting a BR's tests fails `traceability`.

## 10. Risks

- **Stryker with Playwright as test runner is slow.** Acceptable for a small app; if it grows, run mutation nightly instead of per PR.
- **Playwright agent behaviour can change between versions.** `init-agents` output is committed; upgrades go through `/change-framework`.
- **One person holds all roles.** The checks are real but prove nothing about separation of duties until more users are added to `roles.json`.
